# Architecture review — Creation Flow

Architecture review of the creation flow across the TOLOM platform — the end-to-end process of creating new entities (customers, vehicles, work orders, expenses, services, inventory parts/suppliers/POs, appointments, estimates, etc.). Covers the frontend pages and components, client-side state, API routes, service layer business logic, and shared infrastructure.

Trigger: Post-phase audit of creation/mutation flows to identify structural improvements, consistency gaps, and refactoring opportunities before Phase 2 feature work.

## Methodology principles

### M1 — Sheet-over-page creation principle

**Origin:** L0-01 triage: user stated "use sheet, i prefer sheet on creation, and make that accessible from anywhere".

**Rule.** Creation flows MUST use side panels (Sheets) that overlay the current view, never navigate to a separate page. The user stays in context. Sheets must be triggerable from any page via a global registry. Full-page forms are reserved only for exceptionally complex multi-step workflows (e.g., work order wizard with 7+ sections).

### M2 — Centralize cross-cutting concerns in wrappers

**Origin:** L3-01 (rate limiting), L0-05 (error handling), L3-02 (permission enforcement) — all converged on moving cross-cutting logic into `createRouteHandler` or shared wrappers.

**Rule.** Cross-cutting concerns (rate limiting, auth, permissions, error formatting) MUST NOT be duplicated in each handler. They belong in `createRouteHandler` as options (e.g., `rateLimit: true`). If a wrapper can't express it, create middleware, not copy-paste. Duplication is a design smell that signals the wrapper API needs extension.

### M3 — Query-first data fetching principle

**Origin:** L0-03 (inconsistent fetch patterns), L1-02 (inline fetch in CustomerForm) — multiple findings converged on eliminating raw fetch() for server communication.

**Rule.** All API calls MUST go through React Query hooks or mutations. Raw fetch() is forbidden except in React Query hook definitions themselves. React Query provides caching, deduplication, retry, and unified loading/error state — skipping it duplicates this infrastructure in every component.

### M4 — Reusable form component pattern

**Origin:** L1-01 (ResponsiveFormModal), L0-02 (vehicle-form extraction), L0-04 (shared header).

**Rule.** Creation form logic MUST live in standalone `{Entity}Form` components that accept `onSuccess`/`onCancel` callbacks and a `mode` prop (quick vs full). These forms are wrapped by `ResponsiveFormModal` for Sheet/Drawer/Dialog behavior. The page/sheet layer is a thin shell — all form logic lives in the component, making it testable, reusable, and swappable between page and Sheet contexts.

Entry points for the creation flow. Customers and appointments delegate to Sheets via redirects (customers) or direct Sheet rendering (appointments). Work orders use a wizard wrapper that delegates all state to WizardProvider. The remaining pages are standalone full-page forms with inline validation, state management, and submission logic.

### L0-01 — Customers/new redirect stub is dead code

**Evidence**

`customers/new/page.tsx:1-14`

```tsx
export default function NewCustomerRedirect() {
  const { replace } = useRouter();
  useEffect(() => { replace("/dashboard/customers?new=1"); }, [replace]);
  return null;
}
```

The redirect pushes `?new=1` but `customers/page.tsx` never reads search params. The `setNewCustomerDialogOpen(true)` state from `usePageHeader()` is also never consumed — no component reads `isNewCustomerDialogOpen`. The Sheet never opens.

**Current state**

Dead redirect page that redirects to a no-op. The creation Sheet can only be triggered via the page-header button, but even that wiring is broken — the open state is set but never consumed.

**Desired state**

All creation flows should use Sheets (side panels) accessible from anywhere in the app, without navigating away from the current page. Redirect stubs serve as URL targets when navigated to directly.

**Proposed improvement**

- Keep the `customers/new` route as a URL target
- Wire up the page to read `new=1` search param (via `useSearchParams` or `nuqs`) and open the creation Sheet
- Make creation Sheets globally accessible (shared dialog registry or portal pattern)
- Fix `setNewCustomerDialogOpen` → `isNewCustomerDialogOpen` wiring so the button-driven flow also works

- **Severity:** Med
- **Effort:** M
- **Blast radius:** internal
- **Class:** redesign
- **Status:** **accepted** — Keep redirect stub as URL target, wire up search param → Sheet, make Sheets globally accessible
- **Depends on:** —
- **Cross-cut tag:** `T1-global-creation-sheets`

### L1-03 — No global creation Sheet registry / portal

**Evidence**

All creation sheets are opened via props (`open`, `onOpenChange`) from individual pages. There's no way to open a creation sheet from a global context (e.g., from the sidebar, from a notification, from a different page). This conflicts with the user's desire to create from anywhere.

**Current state**

Each Sheet is rendered inside the page that needs it. To open a customer creation sheet from the vehicle form, you need to navigate or pass callbacks through multiple component layers.

**Desired state**

A global creation Sheet registry — a context provider at the app layout level that handles opening/closing any creation sheet from anywhere in the app.

**Proposed improvement**

- Create a `CreationSheetProvider` context (similar to `usePageHeader` pattern but for creation sheets)
- Supports: `openCreateCustomer()`, `openCreateVehicle(customerId?)`, `openCreateExpense()`, etc.
- Renders all sheets at the layout level, only mounting the currently open one
- Components call `const { openCreateCustomer } = useCreationSheets()` to open any sheet

- **Severity:** Med
- **Effort:** L
- **Blast radius:** internal
- **Class:** redesign
- **Status:** **accepted** — Add global creation Sheet registry with context provider
- **Depends on:** L1-01 (sheets unified on ResponsiveFormModal first)
- **Cross-cut tag:** `T1-global-creation-sheets`

### L3-01 — Rate limiting boilerplate duplicated across all mutation routes

**Evidence**

Every POST/PATCH/DELETE handler has this block (8 lines):
```ts
const ip = request.headers.get("x-forwarded-for") ?? "unknown";
const rateCheck = mutationRateLimiter.check(ip);
if (!rateCheck.allowed) {
  return NextResponse.json(
    { error: { code: "RATE_LIMITED", message: "Too many requests" } },
    { status: 429, headers: { "Retry-After": String(Math.ceil((rateCheck.resetAt - Date.now()) / 1000)) } },
  );
}
```
This appears in ~20+ handler files (every POST, PATCH, and DELETE).

**Current state**

~160 lines of duplicated boilerplate across the API surface. Adding a new mutation route requires copying the same block.

**Desired state**

Rate limiting is a cross-cutting concern handled by `createRouteHandler` as an option.

**Proposed improvement**

- Add a `rateLimit?: boolean` option to `createRouteHandler`
- Move the mutation rate limiter check into the wrapper, applied when `rateLimit: true` is set
- Reduces each POST handler by ~8 lines

- **Severity:** Med
- **Effort:** M
- **Blast radius:** public-API
- **Class:** polish
- **Status:** **accepted** — Move rate limiting into createRouteHandler

## Cross-cutting themes

### T1 — Global creation sheet system (active)

**Findings:** L0-01, L1-01, L1-03.

Creation flows should use Sheets accessible from anywhere. Currently, sheets are inconsistently implemented (some use ResponsiveFormModal, some build raw Sheets). A global creation sheet registry would let any component or page open any creation flow without prop-drilling or navigation. This is the highest-leverage change — it affects the entire UX paradigm for creation.

### T2 — Standard form component architecture (active)

**Findings:** L0-02, L0-04, L1-01, L1-04.

Forms should be reusable components with a consistent shell (ResponsiveFormModal + CustomerForm/VehicleForm/etc.). The vehicle form needs extraction, the wizard context needs decomposition, and all creation sheets need unification on the same pattern. This theme surfaces across nearly every finding in Layers 0-1.

### T3 — React Query standardization (active)

**Findings:** L0-03, L0-05, L1-02.

Creation pages inconsistently use raw fetch() vs React Query. Standardizing on query hooks removes manual state management (setSaving/setError), adds caching and retry, and enables consistent error handling.

### T4 — API consistency (closed by L3-01 + L3-02)

**Findings:** L3-01, L3-02, L4-01.

Rate limiting and permissions are applied inconsistently across the API. Moving rate limiting into createRouteHandler and filling missing permission checks will make the API surface uniform and secure. L3-01 addresses rate limiting; L3-02 addresses permissions.

### T5 — Security (closed by L3-02)

**Findings:** L3-02.

Missing route-level permission checks on expense, service, and inventory routes create authorization gaps. Adding requiredPermission to all mutation routes closes these gaps.

### T6 — Service layer hygiene (active)

**Findings:** L4-01, L4-02.

Services create their own Supabase clients (violating documented conventions) and work-order-service is overgrown (930 lines). Refactoring to dependency-injected clients and splitting the large service improves testability and maintainability.
