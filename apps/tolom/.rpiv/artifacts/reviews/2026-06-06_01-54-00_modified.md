## 🔴 Critical

### I2 🔴 bay-view-service omits inventory deduction + cache invalidation on "Completed" status `[cascade: duplicate-processing]`

**Where**
`src/lib/services/bay-view-service.ts:695-760` vs `src/lib/services/work-order-workflow.ts:107-170`

**Code**
```typescript
// bay-view-service.ts — what bay-view calls (NO inventory deduction, NO dashboard/reports invalidation)
// Sets completed_at, invalidates only: bayView, workOrder, workOrderDetail

// work-order-workflow.ts:132-161 — what SHOULD be called (inventory deduction + full cache invalidation)
if (newStatus === "Completed") {
  // ... inventory deduction logic ...
  const { error: mvError } = await supabase.from("inventory_movements").insert(movements);
}
revalidateTag(cacheTags.dashboardMetrics(orgId), "max");
revalidateTag(cacheTags.reports(orgId), "max");
if (newStatus === "Completed") {
  revalidateTag(cacheTags.inventoryMovements(orgId), "max");
  revalidateTag(cacheTags.inventoryBalances(orgId), "max");
}
```

**Why**
Two independent implementations of `updateWorkOrderStatus` exist — one in `work-order-workflow.ts` (canonical, performs inventory deduction + full cache invalidation) and one in `bay-view-service.ts` (incomplete, only sets `completed_at` and invalidates bayView/workOrder/workOrderDetail). The bay-view action handler at `_bay-action-handlers.ts` calls the bay-view version. Every work order completed from bay view silently skips inventory deduction (phantom stock) and leaves dashboard/reports cache stale until 300s TTL expiry.

**Fix**
Delete `updateWorkOrderStatus` from `bay-view-service.ts` and have `_bay-action-handlers.ts` import and call the canonical version from `work-order-workflow.ts` instead.

### I3 🟡 ResponsiveFormModal footer only renders in Desktop path; mobile loses all submit/cancel buttons `[subsumed-by Q1, Q2]`

**Where**
`src/components/ui/responsive-form-modal.tsx:86-99` (Drawer), `:108-125` (Dialog), `:141` (DetailSheet)
`src/components/vehicles/new-vehicle-sheet.tsx:60`

**Code**
```tsx
// responsive-form-modal.tsx:86-99 — Mobile Drawer path — NO footer reference
if (isMobile) {
  return (
    <Drawer open={open} onOpenChange={onOpenChange}>
      <DrawerContent className="max-h-[92vh] flex flex-col">
        <DrawerHeader>...</DrawerHeader>
        <ScrollArea>
          <div className={cn("py-2", className)}>{childrenWithClose}</div>
        </ScrollArea>
      </DrawerContent>
    </Drawer>
  );
}

// responsive-form-modal.tsx:141 — Desktop DetailSheet path — footer rendered here only
{footer && <DetailSheet.Footer>{footer}</DetailSheet.Footer>}
```

**Why**
`NewVehicleSheet` passes `showButtons={false}` to `VehicleForm` (relying on the parent's `footer` prop for submit/cancel buttons) and passes `footer` to `ResponsiveFormModal`. The component has 3 render paths: Mobile Drawer (no footer slot), Desktop Dialog (no footer slot), and Desktop DetailSheet (footer rendered). On mobile, the Drawer path ignores the `footer` prop entirely — VehicleForm internal buttons are disabled, and no footer is rendered. Result: zero submit/cancel buttons in the mobile Drawer. The prop docstring at line 38 explicitly says "desktop only" but this is not enforced or documented for consumers.

**Fix**
Render `{footer}` in the Mobile Drawer path (before `</DrawerContent>`) and optionally in the Dialog path. Or document the limitation and disable `showButtons={false}` when not in DetailSheet mode.

### I1 🟡 Branch filter cache tag co-tenant gap — mutations invalidate `dashboard:${orgId}:all` but never branch-scoped entries

**Where**
`src/lib/cache/keys.ts:19`, `src/lib/services/work-order-items-service.ts:99`, `src/lib/services/work-order-workflow.ts:166`

**Code**
```typescript
// cache/keys.ts:19 — tag generator supports optional branchId
dashboardMetrics: (orgId: string, branchId?: string) =>
  branchId ? `dashboard:${orgId}:${branchId}` : `dashboard:${orgId}:all`,

// work-order-items-service.ts:99 — all 6 mutations invalidate without branchId
revalidateTag(cacheTags.dashboardMetrics(orgId), "max");

// report-service.ts:1888 — server fetch registers WITH branch-scoped tag
tags: [cacheTags.dashboardMetrics(orgId, resolvedBranchId ?? undefined)],
```

**Why**
Server-side fetch cache entries are registered with branch-scoped tags (e.g., `dashboard:org:abc`), but all 7 mutation sites invalidate only the org-wide tag (`dashboard:org:all`). The branch-scoped cache entry persists until its 300s TTL expires. Client-side realtime subscriptions trigger a React Query refetch, but the re-fetch hits the server which returns the still-valid branch-scoped cached response.

**Fix**
Pass the current branch ID to `revalidateTag(cacheTags.dashboardMetrics(orgId, branchId))` in all mutation functions, or invalidate all branch variants by listing them.

**Why**
The `footer` prop exists in the type signature and consumers can pass it, but the Dialog branch (triggered by `useDialogOnDesktop={true}`) silently discards it. This is a false-prop promise: the type system accepts the prop, but the runtime ignores it for 2 of 3 render paths.

### Q3 🟡 work-order-items-service multi-step commitment without transaction boundary

**Where**
`src/lib/services/work-order-items-service.ts:95-100` (addServiceToWorkOrder), `:196-201` (addPartToWorkOrder), and 4 more identical blocks

**Code**
```typescript
// work-order-items-service.ts:95-100 — the pattern, repeated 6 times
const { recalculateWorkOrderTotals } = await import("./work-order-service");
await recalculateWorkOrderTotals(db, workOrderId);
revalidateTag(cacheTags.workOrder(workOrderId), "max");
revalidateTag(cacheTags.workOrderDetail(workOrderId), "max");
```

**Why**
All 6 mutation functions perform DB write → `recalculateWorkOrderTotals` → 4 `revalidateTag` calls without a try-catch around revalidation. If `recalculateWorkOrderTotals` succeeds but a revalidation call fails (edge function timeout, network error), cached dashboard/reports data becomes stale with no retry mechanism.

**Fix**
Wrap the revalidation block in a try-catch with error logging, or use Next.js `revalidateTag` batch API if available.

### Q9 🟡 work-order-workflow multi-step commitment — inventory failure swallowed, execution continues

**Where**
`src/lib/services/work-order-workflow.ts:132-170`

**Code**
```typescript
// work-order-workflow.ts:153-161 — inventory failure caught but not rethrown
} catch (err) {
  reportServerError(
    `[WO ${id}] Failed to deduct inventory: ${err instanceof Error ? err.message : err}`,
  );
}
// Cache invalidation runs unconditionally after the catch block
revalidateTag(cacheTags.dashboardMetrics(orgId), "max");
revalidateTag(cacheTags.reports(orgId), "max");
```

**Why**
When inventory deduction fails (e.g., insufficient stock, Supabase error), the error is logged but execution continues. The work order status is still marked "Completed" and dashboard/reports caches are invalidated to show updated revenue — but the inventory was never deducted. This creates a revenue-overcount: the dashboard shows the sale, but inventory still shows the parts as in-stock.

**Fix**
Either rethrow after logging (mark status update as failed), or add a compensating action that adjusts the status back to a pre-completion state on inventory failure.
