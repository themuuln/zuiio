## Goal

Admins can see and act on the existing approval pipeline from the UI. The RPCs exist; the UI now wires them into a review tab on the game detail page.

## Why

Source submissions and revision requests pile up in the database with no interface to review them. The RPCs `cmd_approve_source`, `cmd_create_revision`, and `cmd_approve_revision` exist but are only callable via raw SQL. Without this UI, the correction workflow is unusable by league staff — every correction requires a database admin. This task is the gateway to operational corrections.

## Design Decisions

- **Service-role reads for admin API**: admin API routes use the server Supabase client (service-role) to bypass RLS for listing submissions/revisions. This is intentional — RLS is designed for the public/anonymous access patterns; admin views need unfiltered access to all records.
- **Confirmation dialogs, not immediate actions**: approval is irreversible (it triggers projection rebuild). Every approval action requires explicit confirmation to prevent accidental clicks.
- **TanStack Query for data fetching in client components**: the review tab is a `"use client"` component; it uses TanStack Query to fetch from the admin API routes and manage loading/error/empty states. Invalidation on mutation ensures the list reflects the new state without a manual refresh.
- **RPCs manage state transitions**: `cmd_approve_source` changes submission status and creates a revision if data differs; `cmd_approve_revision` closes the revision loop and triggers downstream effects. The UI never directly updates submission or revision status.

## Risks & Gotchas

- **Evidence bucket RLS**: if the evidence bucket's RLS policy is incorrectly configured, admins may not be able to download attached evidence files. Verify with a test upload + download from the admin browser session.
- **RPCs not yet migrated**: `cmd_approve_source`, `cmd_create_revision`, `cmd_approve_revision` are defined in `20260712010000_paid_pilot_publication.sql` which is NOT yet applied to the hosted project. The UI routes and components compile and build, but the RPCs will return 404 until the migration is applied.
- **Seed data requirements**: end-to-end testing requires a submission in the seed data with known game_id and status. Extend `seed.sql` if the current seed doesn't include a test submission that the review UI can display and approve.
- **Duplicate approvals**: calling `cmd_approve_source` twice should be idempotent (second call gracefully rejects with "already approved"). Verify this in the RPC implementation — if it raises an error, the UI should display it gracefully via the sonner toast.
