## Goal

A single private admin page (`/admin/ops`) showing pilot health: active tracker sessions, pending submissions and revisions, audit log, stale games, and error reports. Each section is data-driven (read-only, service-role on server) and updates on page refresh. Red badges highlight staleness alarms.

## Why

Without an ops console, the league admin has no way to check the system's health at a glance. They must manually query the database or navigate multiple pages to find: Are there pending submissions that need review? Are any tracker sessions stuck open? Are any games in `final_pending_review` longer than 24 hours? The ops console surfaces all of this on one page, enabling proactive operations instead of reactive firefighting.

## Implementation Steps

1. **Create admin API route** (`src/app/admin/api/ops/route.ts`):
   - Auth check: `supabase.auth.getUser()` → 401 if not authenticated
   - Server-side Supabase client (service-role) for unfiltered reads
   - Query sections:
     - Active `tracker_sessions`: sessions where `status = 'active'` or `ended_at IS NULL`
     - Pending `source_submissions`: `COUNT(*) WHERE status = 'pending'`
     - Pending `game_revisions`: `COUNT(*) WHERE status = 'pending'`
     - Last 50 `audit_log` rows: ordered by `created_at DESC`
     - Stale games: `SELECT * FROM games WHERE status = 'final_pending_review' AND updated_at < NOW() - INTERVAL '24 hours'`

## Design Decisions

- **Server-rendered with service-role reads**: the ops page is `"use server"` — it fetches data at request time via a server-side Supabase client with the service-role key. This avoids the need for an intermediate API route (the route was created but could be bypassed for SSR). The data is always fresh and auth is checked before rendering.
- **Separate API route for potential client consumption**: the `/admin/api/ops/route.ts` route exists independently in case a future client-side dashboard needs to poll ops data without full page reloads. The SSR page currently reads directly from the server client.
- **Red badge for stale games**: the most critical ops signal is "a game has been pending review for over 24 hours." This gets a red background/badge to catch the admin's eye immediately. Other sections use neutral styling.
- **Service-role bypasses RLS intentionally**: ops data is admin-only and unfiltered. The auth check at the route level ensures only authenticated admin users can access this page. RLS is designed for public access patterns and would incorrectly filter admin queries.
- **Not real-time**: the ops console is a request-time snapshot, not a live-updating dashboard. Real-time updates are Phase 5 scope. For now, the admin refreshes the page to see current state.

## Risks & Gotchas

- **`tracker_sessions` table may not have a `status` column**: depending on the session's schema, active sessions may be identified by `ended_at IS NULL` rather than a `status` column. Check the table schema before writing the query. Update: the spec says "active sessions" — confirm the column or condition that defines "active."
- **Pagination for audit log**: the last 50 audit log entries may not be enough during a busy pilot day. Consider making the limit configurable or adding a "view all" link to a dedicated audit log page. For now, 50 is sufficient for the ops overview.
- **Seed data must include diverse states**: the verification requires seed data that covers all ops console sections:
  - An active tracker session (requires `tracker_sessions` row with `ended_at = NULL`)
  - A pending source_submission and game_revision
  - At least one audit_log entry
  - A game in `final_pending_review` with `updated_at` > 24h ago
  - An error report in `public_error_reports`
- **Auth check failure mode**: if `supabase.auth.getUser()` throws (e.g., network error during SSR), the page should render an error state, not crash. Handle the error gracefully with a "Failed to load ops data" message.
- **Multiple active sessions per game**: the spec says "active tracker sessions" — if a game can have multiple sessions (e.g., after handoff), the table should show all active ones, not just one per game.
