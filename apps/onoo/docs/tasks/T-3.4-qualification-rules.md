## Goal

One hot game can't top a per-game leaderboard.

## Why

Per-game averages are misleading when a player has only 1–2 games. Qualification thresholds ensure leaderboard integrity — a 30-point performance in a single game shouldn't rank above someone averaging 20 over 10 games.

## Design Decisions

- Threshold formula `GREATEST(3, CEIL(0.5 * team_games_played))` means:
  - Teams with 0–5 games: requires 3 games minimum
  - Teams with 6+ games: requires at least half the team's games
- `qualified` is computed in the view, not stored — recalculates automatically as the season progresses.
- The expandable section uses the shadcn Dialog component pattern or a simple details/summary HTML element for lightweight toggle without JS overhead.

## Risks & Gotchas

- `v_public_leaders` is consumed by Task 2.7 radar charts and Task 3.3 podium — the new view must be a strict superset of existing columns. No column can be renamed, dropped, or have its type changed.
- The `team_games_played` count must count only games where the team participated (either home or away) with status `league_verified|official`, not all games in the competition.
- `GREATEST` and `CEIL` are standard Postgres — no extension needed.
- Seed data for 30-point-in-1-game: ensure `stat_events` has made-shot events totaling 30 points for that player in one game, and that game has the correct status.

## Notes

The qualification threshold (`GREATEST(3, CEIL(0.5 * team_games_played))`) is a sensible default. The spec allows future customization — if a `competitions.min_games` column is added, the view could reference it instead of the hardcoded threshold.
