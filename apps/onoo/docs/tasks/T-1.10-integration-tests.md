## Goal

Prove recovery under network failure, server rejection, and crash/reload scenarios — mechanically, with automated tests. Core chaos tests simulate random ack/reject/timeout sequences against the `EventQueue` and assert invariants (no op lost, no op double-applied). An integration shell script seeds a game, records events via `cmd_record_event`, voids one, transitions to review, approves a revision, rebuilds the projection, and asserts `v_public_box_score` totals match an independently computed expectation.

## Why

The entire Phase 1 foundation — journal durability, ruleset validation, projection rebuild, authorization cutover — is only as reliable as its tests. Without chaos/integration tests, every failure mode is discovered during the live paid pilot, which erodes trust. These tests prove the system works end-to-end under realistic failure conditions: events arriving out of order, network drops mid-send, duplicate `operation_id`s, and full replay from seed data.

## Implementation Steps

1. **Write chaos tests** (`packages/core/src/sync/__tests__/event-queue.chaos.test.ts`):
   - Use the same mock IndexedDB as T-1.6 journal durability tests
   - Generate random ack/reject/timeout sequences:
     - Enqueue N events (N = 10-50 per run)
     - Simulate random acks (some succeed immediately, some after retry)
     - Simulate random rejections (with various error codes)
     - Simulate timeouts (event stays pending, retry logic triggers)
   - Assert invariants after each sequence:
     - **No op lost**: count of acknowledged + rejected + pending == N
     - **No op double-applied**: each `operation_id` appears at most once in the acknowledged set
     - **Rejection preserves reason**: rejected ops carry their error code
     - **Ordering preserved**: acknowledged sequence matches enqueue order
   - Run multiple iterations (10+) with different random seeds
   - Edge cases:
     - Empty queue operations (flush, ack, reject)
     - All events rejected
     - All events timed out
     - Duplicate `operation_id` in same batch

2. **Write integration test script** (`scripts/integration-test.sh`):
   - Prerequisites: local Supabase stack running (requires Docker)
   - Steps:
     1. Seed a game with known parameters (teams, players, game configuration)
     2. Record 20 events via `cmd_record_event` (mix of shot types, fouls, etc.)
        - Include some duplicate `operation_id` values → verify idempotency
     3. Void one event via `cmd_void_event`
     4. Transition game to `final_pending_review` via `cmd_transition_game`
     5. Approve the revision via `cmd_approve_revision`
     6. Rebuild projection via `cmd_rebuild_projection`
     7. Query `v_public_box_score`
     8. Assert totals match independently computed expectation (hardcoded based on seed data)
   - Exit 0 on all assertions pass, non-zero with failure details otherwise
   - Document usage at the top of the file

3. **Update runbook**:
   - Add integration test to the pre-season checklist
   - Document the purpose and how to run it
   - Reference the test in the verification section of the runbook

## Design Decisions

- **Chaos tests in `packages/core`, not in the app**: the EventQueue is in `@onoo/core` and runs in a framework-agnostic context (mocked IndexedDB). Chaos tests belong at this level where they can run in Node.js without a browser.
- **Random seeds for reproducibility**: use a seeded random number generator so failing test sequences can be reproduced with the same seed. Log the seed on each run.
- **Integration script vs Vitest**: the integration test is a shell script (`scripts/integration-test.sh`) because it exercises the live database via `psql` and `supabase` CLI, not unit-test abstractions. Vitest integration tests against Supabase are possible but require more infrastructure (transaction-rollback per test). The shell script is simpler and more directly verifiable for this purpose.
- **Independent expectation computation**: the integration test doesn't query `v_public_box_score` and trust it. Instead, it computes the expected totals from the seed data manually (e.g., "5 two-pointers made = 10 points") and asserts the view matches. This catches errors in the projection rebuild itself.
- **Idempotency test**: duplicate `operation_id` values in the test event stream verify the deduplication logic. The assertion is that the box score matches the effective set of events (deduplicated).

## Risks & Gotchas

- **Local stack dependency**: the integration test requires Docker + `supabase db reset`. This is the same blocker as T-1.1. The test script should detect missing prerequisites and exit with a clear error message.
- **Seed data for integration test**: the test script needs to insert a game with known teams, players, and events. If `seed.sql` already has test data, the script can reference known IDs. Otherwise, the script must create its own seed data inline via SQL.
- **Independent expectation must match seed data exactly**: the manual expectation calculation is error-prone. Double-check the math: event type → stat change → aggregated totals. A single off-by-one in the computed value will cause a false-positive test failure.
- **Chaos test performance**: random ack/reject sequences with 10+ iterations of 50 events each may be slow if using real IndexedDB. Use an in-memory mock for speed. If using `fake-indexeddb`, verify it handles the concurrency patterns correctly.
- **`cmd_transition_game` may not allow direct test calls**: if the transition RPC requires a specific auth context (e.g., must be called by the game's assigned scorer), the integration test needs to either bypass auth (test-only helper) or set up the correct auth context. Consider adding a `SECURITY DEFINER` variant of the command for testing, or use the Supabase service-role key.
- **Flaky tests**: random chaos tests can produce rare edge cases that fail. If a test fails once in 20 runs, it found a real bug — investigate, don't re-run. Acceptable failure rate: 0% over 100 runs.
