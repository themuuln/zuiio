## Goal

Confirm the existing IndexedDB journal (already implemented in `src/lib/tracker/queue.ts`, state machine pending → sending → acknowledged|rejected) survives browser reload and replays safely. Prove with core tests that the `EventQueue` handles ack/reject sequences, duplicate acknowledgments (idempotency), and rejection persistence correctly.

## Why

The tracker's reliability depends entirely on the local journal. If queued events are lost on reload, the game's stat record is permanently incomplete. If events replay in the wrong order or duplicate, the box score is corrupted. The IndexedDB journal is the safety net for network failures, browser crashes, and device handoffs — it must be proven correct before the paid pilot.

   - **Duplicate ack (idempotency)**: acknowledge the same `operation_id` twice; verify the second ack does not change state and does not produce an error.
   - **Rejection persistence**: simulate rejection of an event; verify it stays in the `rejected` state with the rejection reason preserved.

   - **Empty queue**: verify operations on an empty queue (flush, ack, reject) are safe no-ops.
   - **Replay after simulated crash**: load persisted state from IndexedDB and verify the queue reconstructs correctly.
   - **Concurrent enqueue**: verify ordering when events are enqueued rapidly.

## Design Decisions

- **Tests in `packages/core/src/sync/`, not in `src/lib/tracker/`**: the `EventQueue` logic is framework-agnostic and belongs with the core package's test suite. The `src/lib/tracker/queue.ts` is the app-specific integration (IndexedDB persistence) on top of the core queue logic.
- **Idempotent ack as explicit test**: ack idempotency is critical because the server replay after handoff may re-acknowledge operations the original device already received ack for. The test proves `EventQueue` handles this without errors.
- **Manual reload test documented, not automated**: testing IndexedDB persistence across page reload requires browser automation (Playwright), which is beyond the scope of these unit tests. The manual test procedure is documented for human QA. Automated browser-level reload tests belong in T-1.10.
- **Rejection preserves reason**: the `rejected` state stores the rejection reason (e.g., `ONOO_SEQUENCE_GAP`, `event_type_not_in_ruleset`). This allows the UI to display specific error messages and the admin to understand why events were rejected.

## Risks & Gotchas

- **IndexedDB API may differ across browsers**: the tests use a mock IndexedDB (fake-indexeddb or similar) to avoid browser dependency. Verify that the mock accurately reflects IndexedDB behavior — some subtle differences (transaction auto-commit timing, QuotaExceededError handling) could mask real bugs.
- **Test environment must be deterministic**: random ack/reject sequences should be seeded for reproducibility. The test suite should pass consistently, not intermittently.
- **Concurrency during IndexedDB transactions**: if the test simulates rapid enqueue from multiple "tabs", verify that the queue's IndexedDB transactions are serialized correctly. The core tests may use a synchronous mock that doesn't expose async bugs.
- **`local_seq` monotonicity across sessions**: if the tracker creates a new session (after handoff), the `local_seq` must continue from where it left off, not reset. Verify this in the queue implementation.
