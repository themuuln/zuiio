## Goal

Prove the migration chain resets cleanly, generated TypeScript types match the schema, and the role-matrix security model holds (anon has no access to base tables, can read public views, and cannot execute privileged RPCs).

## Why

Every subsequent task depends on the schema being exactly as migrations define it. Without a proven local stack, we cannot trust that deployed migrations match the committed types, that the role matrix is enforced, or that `supabase db reset` works for reproducing the database. This is the foundational "it boots" check for the entire data layer.

3. **Verify seed data loads** — confirm `seed.sql` runs after migrations and populates test fixtures (games, players, teams, events, etc.).
4. **Generate types** — run `supabase gen types typescript --local` and diff against `src/lib/supabase/types.ts`. If the file doesn't exist yet (first run), create it from the output. If it differs, commit the regenerated version.
5. **Run role-matrix probe** — using `psql` against the local stack:
   - As `anon`: attempt `SELECT *` on each base table in `PRIVATE_TABLES` — must all fail with permission denied.
   - As `anon`: attempt `SELECT ` on each `v_public_*` view in `PUBLIC_VIEWS` — must all succeed.
   - As `anon`: attempt `cmd_record_event()` — must fail with permission denied or authentication error.
6. **Commit the completed script** — ensure `verify-stack.sh` documents usage at the top. Update `EXECUTION-STATUS.md` to `✅` when done.
7. **Run `--remote` mode periodically** — as a drift-detection measure against the hosted project, especially after applying new migrations via Supabase MCP.

## Design Decisions

- **Two-mode script**: `local_verify()` for full migration+types+role check (requires Docker); `remote_probe()` for role-matrix-only check against the hosted project (read-only, useful for drift detection). The `--remote` mode uses PostgREST with the anon key, not `psql`, making it safe to run on any machine.
- **`src/lib/supabase/types.ts` as canonical path**: designated as the official generated types path. First local run creates it; subsequent runs enforce diff == 0. This file location is referenced by the conventions document.
- **Private tables list extensible**: `PRIVATE_TABLES` array in the script documents every table that should be anon-inaccessible. New tables added by later tasks (e.g., T-1.2, T-1.4) must extend this list.
- **Public views list extensible**: `PUBLIC_VIEWS` array documents every view public consumers use. New views added by later phases (3.8, 4.5, 5.1) must extend this list.

## Risks & Gotchas

- **`ALTER TYPE ... DROP VALUE` not supported by Postgres**: the `20260711094500_v2_recovery.sql` migration was patched to remove this operation — the local and hosted schemas could diverge if the patch is incorrect. Verify that any `DROP VALUE`-dependent code paths don't rely on the removed enum values.
- **Generated types differ from committed**: if the hosted project has drift from the migration chain (13 findings from the first `--remote` run), the types generated locally may differ from the previous committed version. Review each diff carefully — drift should be resolved by applying missing migrations to the hosted project via Supabase MCP, not by committing divergent types.
- **Seed data expectations**: `seed.sql` may reference tables or columns that don't exist in the migration chain yet. If `supabase db reset` fails on seed, the seed file must be fixed before the verify script can pass.
- **Migration ordering**: migration files are applied in filename order (timestamp prefix). If migrations are applied out of order or if the `20260711094500_v2_recovery.sql` migration has dependencies on earlier migrations, the reset may fail or produce unexpected state. Use `supabase migration list` to verify the expected order.
