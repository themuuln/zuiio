## Goal

Public visitors can flag a wrong stat via a dialog; reports are rate-limited per IP per day and land in the admin ops console for review/resolve/dismiss.

## Why

Stats can have errors from source data (paper scoresheets, manual entry). A public reporting mechanism lets the community help catch mistakes. The rate-limited, hash-anonymized intake prevents abuse while enabling productive reports.

## Implementation Steps

1. **Migration**: create `public_error_reports` table (id uuid PK, game_id FK, player_id FK, message text 5-500 chars, contact text, created_at, status text 'open'|'resolved'|'dismissed', reporter_hash text). Enable RLS with no public select policy. Create `cmd_report_public_error(p_game_id, p_player_id, p_message, p_contact, p_reporter_hash)` — SECURITY DEFINER, checks same-day count for hash (max 5), inserts row, returns it. Grant EXECUTE to `anon` role.
2. **Route handler** (`/api/report-error`): POST endpoint. Derives `reporter_hash = sha256(ip + UTC date)` server-side — never stores raw IP. Validates message length. Calls RPC with anon Supabase client. Returns 201 on success, 429 when rate-limited, 400 on validation failure.
3. **Dialog** (`report-error-dialog.tsx`): flag icon button triggers shadcn `Dialog`. Contains textarea (5-500 char validation) + optional contact input + submit. On success: toast "Мэдээлсэнд баярлалаа". On error: toast with error message.
4. **Admin ops console**: "Алдааны мэдээлэл" table showing open reports — game/player context, message preview, created_at, resolve/dismiss buttons. Uses `ErrorReportActions` client component that calls PATCH `/admin/api/error-reports/[id]`.
5. **Admin API route**: PATCH handler that updates `public_error_reports.status` by id. Not a protected table; direct update is acceptable (mirrors existing admin route style).

## Design Decisions

- **SECURITY DEFINER RPC**: the `cmd_report_public_error` function runs with definer permissions, bypassing the table's RLS (which blocks public select/insert). This is the standard Supabase pattern for public insert-only endpoints.
- **Rate limit by IP hash**: 5 reports per reporter_hash per day. The hash is `sha256(ip + YYYY-MM-DD)` — same IP on the same day produces the same hash. The raw IP is never stored.
- **50-reports limit in ops console**: the admin query limits to 50 open reports, newest-first. This prevents the page from loading slowly under heavy usage.
- **No auth required for reporting**: public visitors can report without logging in. The rate limit prevents abuse without a login barrier.
- **FK with ON DELETE SET NULL**: if a game or player is deleted, the report row remains (with null FK) rather than being cascade-deleted — preserves the report audit trail.

## Risks & Gotchas

- **IP behind proxy**: `x-forwarded-for` header may contain multiple IPs. The handler takes the first IP in the chain. Behind a CDN like Cloudflare, this is the visitor's real IP. Behind a corporate proxy, it's the proxy IP — rate limiting still works but is per-proxy rather than per-user.
- **Secret key exposure**: the route handler creates an anon Supabase client inline (`createClient(URL, ANON_KEY)`) — this is safe because anon key is client-side safe and the route only calls a SECURITY DEFINER function. No service_role key involved.
- **Error message leaking info**: the route handler returns `error.message` in the 500 response — this could leak internal details. The RPC throws `"Too many reports today"` which is intentional, but other errors should be generic. Currently returns `error.message` — consider wrapping in production.
- **Table not in migration chain status**: the migration `20260715080802_error_reports.sql` must be applied. It was created after the base migration chain.
