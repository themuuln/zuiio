## Goal

A backup scorer can take over a live game without double-tracking. `cmd_handoff_session` exists — the UI flow (handoff button, dialog, superseded session lock, pending-op flush from old device) is implemented but needs integration verification.

## Why

During a live game, the lead scorer's device may die, the scorer may need a break, or equipment may fail. Without a controlled handoff, the backup scorer's session conflicts with the original session — both devices send events, events get rejected (`ONOO_SESSION_REQUIRED`), and the box score becomes unreliable. A controlled handoff ensures exactly one active session at any time, with the old session's pending operations flushing safely and new operations rejected.

## Design Decisions

- **Full-screen lock, not a toast**: once session is superseded, the device must stop tracking immediately. A full-screen notice is unmistakable and prevents accidental further event recording.
- **Pending ops flush with old session ID**: the server accepts acknowledged operations from superseded sessions but rejects NEW operations. Enforced server-side by `cmd_handoff_session` and `cmd_record_event`.
- **Handoff is one-way**: no "take back" after handoff. The lead scorer must start a new session if they need to track again. This simplifies the state machine.
- **Mongolian UI copy**: button and dialog text use Mongolian (`"Гар шилжүүлэх"`), consistent with the app's Mongolian-first convention.

## Risks & Gotchas

- **`cmd_handoff_session` implementation gaps**: verify the RPC actually marks the old session as superseded and sets a `superseded_by` reference. Read the migration that defines `cmd_handoff_session`.
- **Two browser profiles test complexity**: both devices must use the same anon key but different session tokens. If the tracker creates the session via `cmd_open_tracker_session` which checks `auth.uid()`, both devices must be logged in with different accounts.
- **IndexedDB persistence after lock**: when the old device locks, its IndexedDB ops should still flush. If the lock screen prevents the background flush mechanism, pending ops may never complete. The flush should initiate before showing the lock.
- **Race condition during handoff**: if the old device sends an event at the exact moment the handoff is processed, `operation_id` deduplication in `cmd_record_event` handles it — accepted or rejected, the client retries.
- **`cmd_handoff_session` may not be in applied migrations**: verify the migration defining `cmd_handoff_session` (part of `20260712000000` paid-pilot commands) is applied to the hosted project.
