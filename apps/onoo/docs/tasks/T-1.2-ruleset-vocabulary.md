## Goal

An event whose type isn't allowed by the game's ruleset is rejected at both layers (application-level validation in `@onoo/core` and database-level enforcement in `cmd_record_event`).

## Why

Without ruleset-bound validation, a scorer could record a `shot_4pt_made` in a 3-point-only game or a `foul_ejection` in a league that doesn't track ejections. This corrupts projections, produces meaningless box scores, and breaks public stats. Two-layer validation (app + DB) ensures rejection even if a caller bypasses the tracker's client-side validation.

## Design Decisions

- **Two-layer validation**: core (`@onoo/core`) validates in the application layer before sending to the RPC; the RPC (`cmd_record_event`) validates again at the database layer. This ensures the rule is enforced even if a new client or integration bypasses core validation.
- **`ruleset` param is optional in core**: backward compatibility for any existing callers that don't have ruleset context. Lacking ruleset skips ruleset validation in the application layer — not a security concern because the RPC always validates at the database layer.
- **Exception code convention**: `event_type_not_in_ruleset` follows the existing pattern of named exception codes (`ONOO_*`) throughout the command functions. Front-end surfaces these codes directly to the user in rejection notices.
- **Migration not yet applied to hosted project**: per EXECUTION-STATUS.md, `20260712000000_paid_pilot_commands.sql` and `20260712010000_paid_pilot_publication.sql` are NOT yet applied. Apply via Supabase MCP when ready for pilot.

## Risks & Gotchas

- **`stat_event_types` table schema**: verify whether there is a `ruleset_id` column or a junction table for ruleset-to-event-type mapping. Check `\d stat_event_types` before extending the migration.
- **Ruleset lookup performance**: if `validateEvent` fetches the ruleset on every event (potentially dozens per game), cache the ruleset lookup within the tracker session — rulesets don't change mid-game. At the RPC level the join is cheap.
- **Backward compat with old events**: existing events recorded before ruleset enforcement must not be re-validated on replay. The `operation_id` deduplication path in `cmd_record_event` should skip ruleset check for already-accepted events.
- **Tracker must pass ruleset**: confirm the tracker fetches `ruleset_id` from the game record before the tracking loop starts. If it doesn't, `validateEvent` skips the check and only the RPC enforces it — acceptable but suboptimal (user gets a rejection from the server rather than instant local feedback).
