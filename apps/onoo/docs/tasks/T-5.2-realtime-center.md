## Goal

Score and play-by-play update without reload during live games.

## Why

A live game center that updates in realtime — without polling — is the difference between a scoreboard and a living broadcast. Realtime updates via Supabase Realtime (WebSocket) with a polling fallback make the experience reliable across network conditions.

## Implementation Steps

### Database Layer

1. **Migration — realtime publication:**
   - `ALTER PUBLICATION supabase_realtime ADD TABLE public.games;`
   - Payloads are signals only — RLS may strip columns and that is acceptable
   - The socket only tells the client *when* to refetch; data always comes from curated views

### API Layer

2. **Curated live data route** `src/app/api/games/[id]/live/route.ts`:
   - GET handler: returns `v_public_live_games` row for the game + latest play-by-play page
   - This route is what clients fetch when the socket signals a change
   - Returns: `{ game: { ...v_public_live_games row }, play_by_play: [...] }`

### Client/Hook Layer

3. **`use-live-game` hook:** Create `src/lib/hooks/use-live-game.ts`:
   - Input: `gameId: string`
   - On mount: subscribe to `supabase.channel('game-<id>')` with `postgres_changes` on `games` table filtered to the game ID
   - On `UPDATE` signal: call TanStack Query `refetch()` for the curated data route
   - Timeout: if the channel doesn't reach `SUBSCRIBED` within 5 seconds or errors, fall back to 15s polling of the same route
   - Returns the unified data + loading/error state
   - Encapsulates the subscribe-else-poll logic in one place

4. **Migrate homepage cards:** Update T-3.1's live score cards to use `use-live-game` instead of their 20s polling (replace the `TODO(5.1)` code path).

### UI Layer

5. **`LiveGameCenter` rewrite:** Update `live-game-center.tsx`:
   - Uses `use-live-game` hook for data
   - Displays live score, game clock/time, possession indicator
   - Integrates with the provisional badge (T-5.1)

6. **`PlayByPlayFeed` component:** Create `play-by-play-feed.tsx`:
   - Newest-first event feed
   - Each row rendered via `describeEvent` from `@onoo/core`
   - Auto-prepend on refetch with a subtle highlight animation (CSS transition, no JS animation library)
   - Refs inline: highlight the newest row with a temporary CSS class (`animate-fade-in` or similar via Tailwind)

7. **`OnFireIndicator` component:** Create `on-fire-indicator.tsx`:
   - Computes client-side: player has scored ≥8 points in the current quarter
   - Parses play-by-play events for made shots in the current game quarter
   - Shows a small flame icon (from lucide-react, `Flame` icon) next to the player's name in the feed
   - Recalculates on each data refresh

### Fallback

8. **Keep `src/app/api/live/route.ts`** from T-3.1 as-is — it's the homepage polling fallback. The `use-live-game` hook uses 15s polling as its own fallback when WebSocket fails. These are independent fallback paths for different consumers.

## Design Decisions

- Realtime is signal-only — the WebSocket only tells the client *when* to refetch. Data always comes from curated views through the API route. This prevents data inconsistency between view and API layers.
- TanStack Query's `refetch()` is the trigger — this means caching, deduplication, and stale-while-revalidate all work normally. The socket just replaces the timer.
- 5-second subscribe timeout: short enough that users don't wait long for realtime to kick in, long enough for typical WebSocket connections.
- 15-second polling fallback: conservative enough to not overload the server, frequent enough to feel reasonably live.
- On-fire indicator is purely client-side computation — no DB changes needed. Recalculated from play-by-play on each refresh.
- CSS-only highlight animation — no animation library needed. A simple `@keyframes` fade-in or Tailwind's `animate-pulse` applied briefly via a data attribute.

## Risks & Gotchas

- Supabase Realtime must be enabled at the project level. Check if it's already configured for the onoo Supabase project. If not, enable it in the Supabase dashboard: Database → Replication → enable for `games` table.
- `ALTER PUBLICATION supabase_realtime ADD TABLE public.games` may fail if the publication doesn't exist. Check with `SELECT * FROM pg_publication WHERE pubname = 'supabase_realtime'`. If absent, create it first.
- RLS on `games` table may strip columns from the realtime payload — this is acceptable, the payload is just a signal. Data always comes from the API route.
- Multiple tabs watching the same game create separate subscriptions. This is fine — Supabase Realtime handles multiple channels efficiently.
- The `use-live-game` hook must clean up the subscription on unmount to prevent memory leaks.
