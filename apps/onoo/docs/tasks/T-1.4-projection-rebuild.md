## Goal

Derived tables (`game_player_stats`, `game_team_stats`, `season_player_stats`, `standings`) are rebuilt from approved revision events only, triggered by one SQL command `cmd_rebuild_projection(p_game_id uuid)`. Direct inserts into these tables are blocked; all writes go through the rebuild command.

## Why

Currently, projections are computed by the `derive-game` Edge Function which calls `deriveBoxScore()` from `@onoo/core`. This function writes directly to `game_player_stats` and `game_team_stats`. If an error or incomplete revision is approved, the projections get corrupted with no audit trail. A single SQL command that validates inputs, writes only from approved data, and logs every mutation provides an auditable, reversible rebuild path. This is the safety mechanism for the entire correction pipeline.

## Implementation Steps

1. **Design the command's scope**: per spec, "keep derivation in the edge function, but the edge function must write ONLY via `cmd_rebuild_projection`." The command validates + upserts rows computed by the edge function. Do NOT port `deriveBoxScore` to SQL.

2. **Create migration `cmd_rebuild_projection(p_game_id uuid)`**:
   - `SECURITY DEFINER`, `SET search_path = ''`
   - Validate caller has admin/scorer role for the game (reuse `user_can_*` helpers)
   - Verify the game has at least one approved revision
   - Call `write_audit` with `'rebuild_started'`
   - Accept computed rows from the edge function as JSONB arguments, parse with `jsonb_populate_recordset`
   - `DELETE FROM game_player_stats WHERE game_id = p_game_id`
   - `INSERT INTO game_player_stats` from the parsed rows
   - `DELETE FROM game_team_stats WHERE game_id = p_game_id`
   - `INSERT INTO game_team_stats` from the parsed rows
   - Recompute `season_player_stats` for all players in this game by aggregating all approved game_player_stats for the season
   - Recompute `standings` for the season by aggregating all approved game_team_stats
   - Call `write_audit` with `'rebuild_completed'`
   - `SELECT ... FOR UPDATE` on the game record at the start to serialize rebuilds
   - `REVOKE EXECUTE ... FROM PUBLIC`; `GRANT EXECUTE TO authenticated`

3. **Rewrite the edge function** (`supabase/functions/derive-game/index.ts`):
   - Keep `deriveBoxScore()` call as-is
   - Change the write path: instead of `supabase.from('game_player_stats').insert(...)`, call `supabase.rpc('cmd_rebuild_projection', { p_game_id, p_player_stats: JSON.stringify(rows), p_team_stats: JSON.stringify(teamRows) })`

4. **Wire "Rebuild" button in admin Review tab**:
   - After a revision is approved, show a "Rebuild" button
   - On click: call the edge function endpoint or RPC directly
   - Show loading spinner during rebuild
   - Show sonner toast with success/error result
   - Disable button if no approved revision exists

5. **Verify permissions**:
   - Attempt `INSERT INTO game_player_stats` as any app role → fails
   - The migration includes `REVOKE INSERT, UPDATE, DELETE ON game_player_stats, game_team_stats, season_player_stats, standings FROM authenticated, anon, public`
   - Only `cmd_rebuild_projection` (via `SECURITY DEFINER`) can write

6. **End-to-end verification**:
   - Edit an event via void/replace
   - Re-approve the revision
   - Click "Rebuild" in the admin UI
   - Verify the public box score reflects the edited event

## Design Decisions

- **Edge function holds derivation logic; command holds write path**: `deriveBoxScore()` stays in `@onoo/core` (testable without DB). The edge function calls it, then passes computed rows to `cmd_rebuild_projection`.
- **Delete-and-reinsert, not upsert**: simpler and safer than computing deltas. A crash mid-rebuild leaves the previous state intact (the function runs in a single transaction).
- **`write_audit` at start and end**: enables detection of interrupted rebuilds. If `rebuild_started` is logged but `rebuild_completed` is not, the rebuild failed mid-way.
- **Explicit permissions revoked**: `REVOKE INSERT, UPDATE, DELETE` on derived tables from all app roles ensures only `SECURITY DEFINER` commands can write.
- **Row lock serialization**: `SELECT ... FOR UPDATE` at the start of the command prevents concurrent rebuilds for the same game.

## Risks & Gotchas

- **Race condition**: without `SELECT ... FOR UPDATE`, concurrent rebuilds could interleave delete-and-reinsert. Always lock the game row.
- **JSONB arguments from edge function**: `supabase.rpc()` doesn't accept array-of-composite-type arguments directly. Pass computed stats as JSONB and use `jsonb_populate_recordset` on the SQL side to parse them into typed rows.
- **`season_player_stats` scope**: recomputing ALL season player stats when only one game changed is correct but potentially expensive. Acceptable for pilot scale (< 20 games/season). For larger scale, consider incremental update using the difference between old and new game stats.
- **`derive-game` edge function may not exist in the expected location**: the spec references `supabase/functions/derive-game/index.ts`. If the function was never created or was deleted, implement the write-through-command path without the edge function — call `cmd_rebuild_projection` directly from the admin API route.
- **Approved revision check**: the command must reject rebuilds if no approved revision exists for the game. This prevents rebuilding from events that haven't been reviewed.
