# Architecture

Agent Gateway is a multi-tenant AI agent that connects Telegram users to business data in Zer and Tolom. This document explains the system design, data flow, and key architectural decisions.

## Bot Modes

### Mode A: Shared Bot

A single Telegram bot serves all organizations. Users link their account via a QR code or one-time code.

**Flow:**
1. User opens the bot → `/start` command
2. User scans QR or enters code generated by the Zer/Tolom web app
3. Link stored in `telegram_links` table
4. On every message, `resolveOrgFromChatUser()` looks up the active link by `(chat_id, user_id)`
5. Gateway scopes all queries to the resolved `orgId`

**Key constraint:** Exactly one active link per `(chat, user)` pair. If a user belongs to multiple orgs, the most recently used one is selected.

### Mode B: Custom Bot

Each organization gets its own Telegram bot. No linking needed — the bot IS the organization.

**Flow:**
1. Organization creates a bot via BotFather
2. Bot token stored in `custom_bots` table with a `botKey` (UUID)
3. Webhook URL includes the `botKey` as a route parameter
4. `resolveOrgFromBotKey()` maps the bot to its organization
5. `chatId` and `telegramUserId` are filled per-message from the update

**Key difference:** Mode B has no user-level identity — `userId` defaults to `orgId` since the bot is org-scoped.

## Provider Architecture

The gateway uses a provider pattern where each AI provider owns the multi-turn tool-calling loop.

```typescript
interface AiProvider {
  runWithTools(params: {
    system: string;
    userMessage: string;
    tools: GatewayTool[];
    context: ToolContext;
    maxRounds?: number;
    conversationHistory?: Message[];
  }): Promise<string>;
}
```

### Provider Fallback

The `AiGateway` class wraps primary and fallback providers:

```
User Message
    │
    ▼
┌──────────────┐     failure     ┌─────────────────┐
│ OpenCodeGo   │ ──────────────▶ │  GPT-4o-mini    │
│  (primary)   │                  │  (fallback)     │
└──────────────┘                  └─────────────────┘
```

If the primary provider throws, the error is captured to Sentry and the fallback provider handles the request. If no fallback is configured, the error propagates.

### Tool Wrapping

Gateway tools receive `ToolContext` (orgId, userId, supabase) as a second argument. Providers that don't support context injection (like `@zuiio/ai-agent`'s `runWithTools`) use a wrapper that closes over the context:

```typescript
function wrapTool(tool: GatewayTool, context: ToolContext): Tool {
  return {
    ...tool,
    execute: (args) => tool.execute(args, context),
  };
}
```

This ensures tools always have access to the resolved tenant without the provider needing to know about multi-tenancy.

## Tool System

Tools are the bridge between the LLM and business data. Each tool:

1. **Receives context** — `orgId` (resolved by gateway, never from LLM), `userId`, `supabase` client
2. **Queries Supabase** — using service-role privileges (bypasses RLS)
3. **Filters by orgId** — every query MUST include `.eq("organization_id", orgId)`
4. **Returns structured data** — formatted for LLM consumption

### Tool Lifecycle

```
LLM decides to call tool
        │
        ▼
┌───────────────┐
│  Audit Wrap   │  ← withAudit() adds timing + logging
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  Tool Execute │  ← Receives (args, context)
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  Supabase     │  ← Service-role client, filtered by orgId
│  Query        │
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  Result       │  ← Truncated to maxResultTokens
│  Truncation   │
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  Audit Log    │  ← Fire-and-forget insert to agent_audit_log
└───────────────┘
```

### Write Tools vs Read Tools

- **Read tools** (e.g., `getDailySummary`, `searchCustomers`) execute immediately
- **Write tools** (e.g., `createInvoice`, `updateWorkOrder`) go through the confirmation gate:
  1. Tool returns a summary + staged action
  2. Gateway sends inline keyboard (✅ Confirm / ❌ Reject)
  3. User taps button → callback query
  4. `confirmAction()` or `rejectAction()` called
  5. If confirmed, tool re-executes with the staged args

## State Management

All state is request-scoped and stored in Supabase (no Redis in current deployment).

| State | Storage | TTL | Purpose |
|---|---|---|---|
| Session | `agent_sessions` | 24h | Conversation history per (org, chat, user) |
| Rate limit | In-memory Map | 60s sliding window | Per-org request throttling |
| Budget | `agent_daily_spend` | Daily reset | Token spend tracking per org |
| Audit | `agent_audit_log` | Permanent | Tool call logging |
| Staged actions | In-memory Map | 5 min | Confirmation gate for write tools |

### Session Schema

```typescript
interface SessionMessage {
  role: "system" | "user" | "assistant" | "tool";
  content: string | null;
  tool_calls?: ToolCall[];
  tool_call_id?: string;
}
```

Sessions are capped at `MAX_SESSION_MESSAGES = 50` messages. Older messages are dropped on save.

### Rate Limiting

In-memory sliding window per org:
- **Messages:** 20 per 60-second window
- **Link requests:** 10 per 60-second window

Production note: In-memory rate limiting doesn't work across multiple serverless instances. For consistent limiting, migrate to Redis or use Supabase's `pg_advisory_lock`.

### Budget Controls

Per-org daily token spend with two thresholds:
- **Soft cap:** 500,000 tokens — warning logged
- **Hard cap:** 1,000,000 tokens — requests rejected with user-facing message

Usage is recorded atomically via PostgRPC's `increment_daily_spend` RPC function, falling back to upsert if the function doesn't exist.

## Security Model

### Org Isolation

The gateway resolves `orgId` from the database (via `telegram_links` or `custom_bots`), never from LLM output. This is the core security invariant:

```
Telegram user ──▶ Link table ──▶ orgId (trusted)
                    │
                    ▼
              Tool receives orgId
                    │
                    ▼
              Query filtered by orgId
```

The LLM can request any orgId, but the gateway ignores it and uses the resolved value.

### Input Sanitization

- **Control characters stripped** from user input
- **Display names sanitized** to prevent prompt injection
- **Database errors genericized** — no schema/table/column names exposed
- **Results truncated** to prevent context window overflow

### Supabase Access

Two privilege levels:
1. **Service role** (`createServiceClient`) — bypasses RLS, used by curated tools. Tools MUST filter by `orgId`.
2. **Agent reader** (`createReaderClient`) — RLS enforced, read-only. Used by `runSQL` tool.

Tolom has a separate Supabase project with its own service role key.

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  Vercel /   │────▶│  Next.js Server  │────▶│  Supabase       │
│  Cloudflare │     │  (webhook route) │     │  (Postgres)     │
└─────────────┘     └──────────────────┘     └─────────────────┘
                           │
                           ▼
                    ┌──────────────────┐
                    │  External APIs   │
                    │  - OpenCodeGo  │
                    │  - OpenAI        │
                    │  - Groq (STT)    │
                    │  - Telegram API  │

```

- **Vercel:** Primary deployment target. Set root directory to `apps/agent-gateway`.
- **Cloudflare Workers:** Alternative via OpenNext. Uses `wrangler deploy`.
- **Serverless constraints:** No persistent state in memory. Rate limiter and staged actions are best-effort across cold starts.

## Key Design Decisions

1. **Service-role over RLS** — Tools use service-role to avoid RLS complexity, relying on application-level org filtering. This is simpler and faster but requires discipline in every tool.

2. **Provider owns the loop** — Each provider implements its own multi-turn tool-calling loop rather than a shared abstraction. This allows provider-specific optimizations (e.g., OpenCodeGo's function calling format vs OpenAI's).

3. **In-memory state** — Rate limiting and staged actions are in-memory for simplicity. Acceptable for single-instance serverless; would need Redis for multi-region consistency.

4. **Mongolian-first UX** — All user-facing messages are in Mongolian. System prompts, error messages, and button text are hardcoded in Mongolian.

5. **Two Supabase projects** — Zer and Tolom use separate Supabase projects for data isolation. The gateway routes queries to the correct client based on `productType`.
